# AnomaLens: заметки к статье

## Рабочее название

**AnomaLens: объяснимая система реального времени для мониторинга
промышленного насоса, распознавания типа неисправности и выдачи
рекомендаций по обслуживанию**

Английский вариант:

**AnomaLens: An Explainable Real-Time Monitoring System for Industrial Pump
Equipment with Fault Type Recognition and LLM-Assisted Maintenance
Recommendations**

## Аннотация (черновик)

Предлагается end-to-end система мониторинга промышленного насоса,
объединяющая потоковую обработку телеметрии, обнаружение аномалий,
классификацию типа неисправности, оценку риска и выдачу рекомендаций
оператору. В отличие от работ, ограничивающихся сравнением моделей на
статическом датасете, система демонстрирует полный цикл «данные → объяснение
→ решение» в реальном времени. На открытом датасете SKAB детектор PCA T²+Q
достигает F1 = 0.713, а классификатор пяти типов неисправностей — accuracy
0.936 и macro F1 0.886 при валидации по файлам. Объяснимость обеспечивается
robust z-скорингом датчиков, а рекомендации формируются гибридно: правила
определяют содержание, языковая модель — формулировку. Система реализована
как FastAPI + React и воспроизводится локально.

## Исследовательские вопросы

1. Можно ли построить работающую end-to-end систему мониторинга, а не
   только сравнить модели на статическом CSV?
2. Насколько точно можно определить тип неисправности по 30-секундному окну
   телеметрии при валидации по файлам, а не по случайным окнам?
3. Как объяснить оператору, почему система считает поведение аномальным?
4. Как совместить детерминированные правила и LLM так, чтобы рекомендации
   оставались безопасными и воспроизводимыми?

## Вклад

1. **End-to-end архитектура**: реплей телеметрии → детекция → классификация
   типа → риск → рекомендация → интерфейс оператора.
2. **Классификатор пяти типов неисправностей** на окнах SKAB:
   accuracy 0.936, macro F1 0.886, валидация `StratifiedGroupKFold` по файлам.
3. **Объяснимые тревоги**: robust z-скоры по каждому датчику, top-3 отклонения,
   вклад в решение.
4. **Оценка риска** как комбинация отклонения датчиков, score ratio и
   устойчивости аномалии.
5. **Гибридные рекомендации**: правила задают шаги, DeepSeek переформулирует
   их для оператора; при отказе API используется правило.
6. **Открытый воспроизводимый прототип**: FastAPI, React, SQLite, WebSocket,
   Telegram, звук.

## Методология (кратко)

- **Данные:** SKAB, 35 CSV, 8 датчиков, 1 Гц.
- **Детектор:** PCA, обучение на `anomaly-free.csv`; калибровка T²/Q и порога
  на первых 100 секундах сессии; score = max(T²/T²₉₉, Q/Q₉₉).
- **Объяснение:** robust z = (x − median) / max(1.4826·MAD, 1%·|median|, 10⁻³),
  клип ±25; top-3 датчика.
- **Классификатор:** 30-секундные окна, stride 5, 48 признаков
  (mean/std/min/max/last/slope × 8), RandomForest 400 деревьев,
  `class_weight="balanced_subsample"`.
- **Валидация:** `StratifiedGroupKFold(n_splits=3)` по файлам, чтобы окна
  одного файла не попадали одновременно в train и test.
- **Риск:** 45% отклонение датчиков + 35% score ratio + 20% устойчивость;
  high при |z| ≥ 6 и persistence ≥ 10 с или ratio ≥ 2.
- **Рекомендации:** правила по типу неисправности + DeepSeek (temperature 0.2,
  max_tokens 260), fallback на правила.

## Структура статьи

1. **Введение** — зачем мониторинг насосов, почему недостаточно статического
   бенчмарка, цель системы.
2. **Обзор** — PCA/SPC, Isolation Forest, autoencoders, SKAB, explainable AD,
   LLM в maintenance.
3. **Данные** — SKAB, 8 датчиков, 5 классов, аудит, утечка в официальном split.
4. **Система** — архитектура, поток, модель, классификатор, риск,
   рекомендации, интерфейс.
5. **Эксперименты** — метрики детектора, классификатора, 5 сценариев,
   задержка, ложные тревоги, примеры тревог.
6. **Обсуждение** — почему PCA, почему RandomForest, почему гибридные
   рекомендации, что даёт объяснимость.
7. **Ограничения** — реплей, один стенд, 5 классов, нет RUL, LLM
   недетерминирован, false alarms.
8. **Заключение** — итог, направления развития.

## Отличие от типичной статьи «мы обучили модель»

Статья описывает не только модель, а **систему принятия решений**:

- модель обнаруживает;
- z-скоры объясняют;
- классификатор типизирует;
- риск приоритизирует;
- рекомендация говорит, что делать;
- интерфейс и история обеспечивают рабочий процесс.

Именно эта связка является вкладом, а не отдельный алгоритм.

## Что можно добавить для усиления

- Подключение реального шлюза датчиков (MQTT/HTTP) вместо реплея.
- RUL-прогноз и планирование ТО.
- Cost-sensitive порог: цена пропуска vs цена ложной тревоги.
- Пилот с операторами и оценка полезности рекомендаций.
- Второй датасет (MetroPT-3) для проверки переноса.
- Сравнение с autoencoder/Isolation Forest на том же протоколе.
